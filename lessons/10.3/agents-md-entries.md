# AGENTS.md entries from this lesson

Claude updated the Lab's `AGENTS.md` in this lesson. The client ID line now reads:

Top-level scripts (`market_data.py`, `scanner.py`, `orders.py`, ...) are one-off IB experiments. Each needs its own IB client ID: 1 `connect_test.py`, 2 `ibapi_hello.py`, 3 `market_data.py`, 4 `scanner.py`/`orders.py`, 5 `data_pipeline`, 6 `live` (one process, however many pairs).

and it added these entries to the Layout section:

- `scheduler/`: runs a trading day by itself (`uv run -m scheduler` daemon, `--today [--dry-run]`, `--next N [--from DATE]`; README has the OS equivalents). This machine has no systemd, cron or at, so it is a Python loop: `plan.py` builds the day from the NYSE calendar in New York time (prep 09:00, runner 09:25, flatten = close - 5 min, stop = close + 5 min, so half days end early), `jobs.py` runs `data_pipeline` then `scanner.py` (client IDs 5 and 4), starts `python -m live ... --flatten-before-close-min 5` (client ID 6) for the strategy in `scheduler/schedule.yaml`, restarts it up to `max_restarts` times if it dies before the flatten time (never after a halt, exit 2 or 3, or STOP), and sends it SIGINT at the stop time. The STOP file blocks the runner start and is never cleared by the scheduler; `--clear-halt` and `--flatten-on-mismatch` are never passed. `report.py` writes `data/live/reports/YYYY-MM-DD.md` from files only (no IB connection): jobs, scan top 5, decisions, trades, risk refusals, halt, and NOT FLAT if the state file still shows a position. The scheduler places no orders. Tests: `tests/test_scheduler.py` (fake clock and fake subprocesses).

- `live/` several strategies at once (`uv run -m live --config live/engines.yaml [--once] [--dry-run]`). `live/engines.py` loads the pairs (`engines:` list of strategy, symbol, optional settings; quote times; ONE engine per symbol because IB keeps one position per symbol; every symbol must have limits in `risk_limits.yaml`, checked at load). `live/multi.py` `MultiRunner` runs one ordinary `Runner` per pair in ONE process over ONE IB connection and one client ID (6): separate state files, reconcile, order tags and feeds; they poll in turn in one thread; the risk limits are shared (per-symbol caps, and the trade count and daily loss limit read from IB, so they count all pairs). One pair halting or erroring does not stop the others; the loop ends when all have halted or stopped; STOP stops all. After a reconnect EVERY runner reconciles (`Link.epoch` in `runner.py`), not only the one that reconnected. `live/daily_log.py`: all modules log to the one logger `live`, so the running engine is kept in a context variable and each engine has a `DailyFileHandler` that keeps only its own records: `data/live/<strategy>_<symbol>/logs/YYYY-MM-DD.log` (New York date; log lines and the console view together), records outside any engine go to `data/live/engine/logs/`; the console lines get a `[SYMBOL strategy]` prefix. The one-pair form (`--strategy --symbol`) is unchanged and still writes `events.log`. The scheduler takes either `strategy`/`symbol` or `engines: live/engines.yaml` in `scheduler/schedule.yaml`; it restarts a dead runner unless EVERY pair is halted. Tests: `tests/test_live_multi.py`.

- `live/alerts.py`: push alerts through ntfy.sh to a private random topic. The topic is `NTFY_TOPIC` in the gitignored `.env` (or the environment); `uv run -m live.alerts --init` makes one (never overwrites), `--test` sends one test alert and prints the browser link `https://ntfy.sh/<topic>`, `--link` just prints it. Only that one line of `.env` is read. Anyone who knows the topic can read and post, so the name is the secret; messages are short and carry no account number. Alerts: fills (buy, and the sell with its reason and P&L before costs, once per trade), rejects (IB refusals via `Broker.on_reject`, and risk-limit refusals), halts (also a runner that starts already halted), a lost connection (once per outage) and its return, the kill switch (STOP seen by a runner, once per process; `live.kill` at start and with its result). Never for routine bars, skipped signals or dry runs. Sending is on a background thread with a 5 s timeout and one retry; a failure is only logged and never stops trading; `Alerter.close()` flushes at exit. Without a topic, alerts are off. Tests: `tests/test_live_alerts.py` (fake IB, fake sender, no network).
